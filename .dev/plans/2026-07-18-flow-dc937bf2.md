## 1. Goal

Make firegraph's local SQLite `findNearest` stop re-parsing JSON per candidate row. For fields DECLARED as vectors, store the vector as a Float64 little-endian BLOB in a shadow column `__vec_<field>` and score it with a numeric UDF that decodes the blob via `DataView.getFloat64(offset, true)`. Exact KNN only (brute-force scan). Run-to-run rankings AND distances must be byte-identical to today's JSON path. Applies ONLY to the two local backends: `src/sqlite/local.ts` (better-sqlite3) and `src/sqlite/node-sqlite.ts` (node:sqlite). Undeclared vector fields keep working via the existing pure-JSON path (no speedup, full back-compat).

Why byte-identical holds: JS numbers are IEEE-754 Float64; `JSON.stringify` of a number is round-trip exact, and a Float64 LE blob preserves the identical bits. As long as the blob UDF accumulates `dot` / `sumSq` / `normStored` / `normQuery` in the SAME loop order (i = 0..dim-1) with the SAME formulas as `computeVectorDistance`, every intermediate double is bit-identical, so distances and therefore ordering (including the `doc_id ASC` tie-break) match exactly.

## 3. Detailed approach

### 3.1 `src/types.ts` — IndexSpec.vector

Add an optional field to `IndexSpec`:

```ts
export interface IndexSpec {
  fields: Array<string | IndexFieldSpec>;
  where?: string;
  /**
   * Marks this spec as a vector declaration for the local SQLite backends
   * (firegraph/sqlite-local, firegraph/sqlite-builtin). When set, the backend
   * maintains a Float64 little-endian BLOB shadow column for `field` so
   * findNearest can score without per-row JSON.parse. `field` is a bare
   * data-relative field name (e.g. 'embedding' or 'nested.vec'); `dimension`
   * is the fixed vector length. Ignored by every other backend (Firestore,
   * D1, DO). A vector spec typically carries an empty `fields: []` — it does
   * not create a composite index.
   */
  vector?: { field: string; dimension: number };
}
```

Keep `fields` required in the type (empty array is valid). Document that a vector-only spec uses `fields: []`.

### 3.2 `src/internal/sqlite-schema.ts` — do not feed vector specs to buildIndexDDL

`buildSchemaStatements` (line ~97) currently does:
`const fromRegistry = options.registry?.entries().flatMap((e) => e.indexes ?? []) ?? [];`
then `buildIndexDDL(spec, ...)` per spec. `buildIndexDDL` throws `INVALID_INDEX` on empty `fields`. A vector-only spec (`fields: []`) would crash schema bootstrap.

Fix: filter out vector declarations from the composite-index collection. Change the flatMap to drop specs whose `vector` is set:
`.flatMap((e) => (e.indexes ?? []).filter((spec) => spec.vector === undefined))`
(Equivalently filter after concatenating core+registry, but core has no vector specs, so filtering the registry slice is enough.) This is the single line that keeps the shared schema builder vector-agnostic. The shadow column is added by the JS ensure step in the local factories, NOT here — see 3.5 / refinement build-step 4.

Note: a spec MAY legitimately carry both real `fields` (a composite index) and NOTHING else; only skip when `spec.vector !== undefined`. If an author ever sets both `vector` and non-empty `fields` on one spec, we still skip the composite index for it — acceptable and documented; the convention is one spec per concern.

### 3.3 `src/internal/sqlite-search.ts` — new building blocks

Add these, mirroring the existing FTS helpers' style and the `computeVectorDistance` math exactly.

(a) Shadow-column naming helper:

```ts
export function vectorShadowColumn(field: string): string {
  // Sanitize the bare field name into a safe SQLite column identifier.
  // field is data-relative (no 'data.' prefix). Reuse the same safe-key
  // rule the rest of the module uses (validateJsonPathKey per dotted part).
  // Replace '.' with '_' so 'nested.vec' -> '__vec_nested_vec'.
  return `__vec_${field.replace(/\./g, '_')}`;
}
```

Validate each dotted part of `field` with `validateJsonPathKey` before building the column name (reject exotic keys loudly — same contract as the query path). Keep the mapping injective enough for the declared-field set (dedupe/consistency is enforced in the factory, see 3.6).

(b) `encodeVectorBlob(vec: number[]): Uint8Array` — JS Float64 little-endian encoder:

```ts
export function encodeVectorBlob(vec: number[]): Uint8Array {
  const buf = new ArrayBuffer(vec.length * 8);
  const view = new DataView(buf);
  for (let i = 0; i < vec.length; i++) view.setFloat64(i * 8, vec[i], true); // LE
  return new Uint8Array(buf);
}
```

Bind this as a SQL parameter for the backfill UPDATE. better-sqlite3 accepts a `Buffer`/`Uint8Array` as a BLOB param; node:sqlite accepts a `Uint8Array` cast to `SQLInputValue`. Return `Uint8Array`; in node-sqlite.ts wrap/cast as needed.

(c) `computeVectorDistanceBlob(storedBlob, queryJson, measure): number | null` — the blob-side distance body, math-identical to `computeVectorDistance`:

- Accept `storedBlob` as a `Uint8Array`/`ArrayBuffer`/Node `Buffer` (whatever the driver hands the UDF for a BLOB column). Guard: if not a byte container, return null.
- Parse `queryJson` the SAME way `computeVectorDistance` does — reuse the exact same query-vector memo pattern (module-level `memoQueryJson`/`memoQueryVec`) so query parsing cost stays amortized. (Either share the existing memo variables or a parallel pair — sharing is fine since the query JSON string is identical across both UDFs in a single query.)
- Dimension: `const dim = byteLength / 8`. If `byteLength % 8 !== 0` return null. If `dim !== query.length` return null (dimension mismatch → drop out, same as JSON path).
- Wrap the bytes in a `DataView` (respect the buffer's `byteOffset`/`byteLength` if it is a Node Buffer view: `new DataView(b.buffer, b.byteOffset, b.byteLength)`).
- Loop `i = 0..dim-1`: `const a = view.getFloat64(i*8, true); const b = query[i];` then the IDENTICAL accumulation: `if (!Number.isFinite(a)) return null; if (typeof b !== 'number' || !Number.isFinite(b)) return null; dot += a*b; const diff = a-b; sumSq += diff*diff; normStored += a*a; normQuery += b*b;`
- Same switch: EUCLIDEAN = `Math.sqrt(sumSq)`; COSINE = `1 - dot/(Math.sqrt(normStored)*Math.sqrt(normQuery))`, null if denom === 0; DOT_PRODUCT = `dot`; return `Number.isFinite(result) ? result : null`.
  Export it for direct unit testing (parity with `computeVectorDistance`).

(e) Null-on-change trigger DDL builder — PURE SQL, AFTER UPDATE ONLY, WHEN-guarded (refinement 2):

```ts
export function buildVectorNullOnChangeTrigger(table: string, field: string): string {
  const t = quoteIdent(table);
  const col = quoteIdent(vectorShadowColumn(field));
  const name = quoteIdent(`${table}__vec_${field.replace(/\./g, '_')}_nullonchange`);
  return `CREATE TRIGGER IF NOT EXISTS ${name} AFTER UPDATE ON ${t}
  WHEN new."data" IS NOT old."data" BEGIN
  UPDATE ${t} SET ${col} = NULL WHERE "doc_id" = new."doc_id";
END`;
}
```

Rationale baked in: SQLite can't assign `NEW.col` directly, so we issue a real UPDATE of the shadow col keyed by `doc_id`. Recursive triggers are OFF by default, so this UPDATE does not re-fire the trigger. The `WHEN new.data IS NOT old.data` guard is essential: the read-path backfill UPDATE touches ONLY the shadow column (not `data`), so `new.data IS old.data` is true there and the trigger does NOT fire — the backfill we just wrote is not self-invalidated. INSERT needs NO trigger (a freshly added column defaults NULL, so the JSON branch serves new rows until the next backfill).

(f) JS ensure/backfill statement builder(s). Provide pure functions that the factories call; keep SQL construction here, execution in the factory. Suggested shape (return SQL strings / small structs; the factory binds params and runs them, so read-only guarding lives at the execution site):

```ts
export function vectorAddColumnSql(table: string, field: string): string {
  // ALTER TABLE <t> ADD COLUMN "__vec_<field>" BLOB
  return `ALTER TABLE ${quoteIdent(table)} ADD COLUMN ${quoteIdent(vectorShadowColumn(field))} BLOB`;

export function vectorBackfillSelectSql(table: string, field: string): string {
  // rows needing a blob: shadow col IS NULL AND the JSON field is present
  const col = quoteIdent(vectorShadowColumn(field));
  return `SELECT "doc_id", json_extract("data", '$.${field}') AS v
          FROM ${quoteIdent(table)}
          WHERE ${col} IS NULL AND json_extract("data", '$.${field}') IS NOT NULL`;
}
export function vectorBackfillUpdateSql(table: string, field: string): string {

  return `UPDATE ${quoteIdent(table)} SET ${col} = ? WHERE "doc_id" = ?`;

```

### 3.5 Thread declarations into the wrapper + JS ensure/backfill (both factories, IDENTICAL)

`wrapLocalSearchBackend` currently takes `(inner, executor, rootTable)`. Extend it to also receive the collected vector declarations, e.g. `(inner, executor, rootTable, vectorDecls)`. In `createLocalSqliteBackend` / `createNodeSqliteBackend`, compute `const vectorDecls = collectVectorDeclarations(options.registry)` (registry is in `backendOptions.registry`) and pass it in. Propagate `vectorDecls` through the `subgraph()` re-wrap so subgraph tables get the same treatment.

Add a per-resolved-table JS ensure step inside the wrapper, mirroring how `runWithSchema` / `healableTables` resolve per-table (each wrapper instance is bound to one `inner.collectionPath`). Cache the result on the wrapper instance (a `let vecEnsured: Promise<VecEnsureResult> | null`), analogous to `SqliteBackendImpl.ensured`. The ensure step, per declared vector field, does — AFTER `inner.ensureReady()` so the base table exists:

1. `PRAGMA table_info(<table>)` → does `__vec_<field>` already exist?
2. If missing: attempt `ALTER TABLE <t> ADD COLUMN "__vec_<field>" BLOB`. This is the ONLY non-idempotent statement — run it OUTSIDE the chunked extraTableDDL transaction (which aborts on error), guarded by the table_info check so a second run is a no-op. On any write failure (read-only DB, or a lost race where a concurrent connection added it — catch "duplicate column name" too), treat the column as absent-for-this-handle and DO NOT mark it materialized (see refinement 3).
3. If (and only if) the column now exists: create the null-on-change trigger via `buildVectorNullOnChangeTrigger` (CREATE TRIGGER IF NOT EXISTS — idempotent, but must come AFTER the column exists since it references it).
4. Backfill: run `vectorBackfillSelectSql`; for each row, in JS: parse the JSON value (it comes back as a JSON string from `json_extract` of an array — `json_extract` of a JSON array returns the JSON text; parse it), validate it is an array of finite numbers with `length === dimension` (skip / leave NULL on mismatch — this is where dimension validation lives, refinement 1/4), `encodeVectorBlob`, then `vectorBackfillUpdateSql` binding `[blob, doc_id]`. Batch these updates (reuse `executor.batch` / the driver's transaction) but keep each write read-only-guarded — if the DB is read-only the first UPDATE throws; catch and abort the backfill for this handle (fall through to JSON path).
5. Record, per field, whether the shadow column is materialized (exists) on THIS handle. The ensure result is the `DeclaredVector[]` (field, dimension, shadowColumn) for ONLY the fields whose column exists — this is exactly what `compileFindNearest` needs.

Read-only detection (refinement 3): the simplest robust approach is "try the write, catch the failure." Wrap steps 2–4 in try/catch; on a write error that indicates read-only (`SQLITE_READONLY`, "attempt to write a readonly database", or "readonly") OR any write failure during ensure, mark all not-yet-materialized fields as NOT materialized and return. Do NOT let the error escape `findNearest`. Optionally detect up front (better-sqlite3 exposes `db.readonly`; node:sqlite has no such property — probe via a harmless write or just rely on catch). Belt-and-suspenders: also guard so that if `table_info` already shows the column present (added by a writable connection earlier), a read-only handle still marks it materialized and uses the blob path for reads (reads on a read-only DB are fine).

Then in `findNearest`:

Order the ensure BEFORE `runWithSchema`/compile so compileFindNearest only references a shadow column that provably exists (refinement 3 — never emit SQL referencing a missing column). If `materialized` is empty, `compileFindNearest` emits the exact pure-JSON statement as today (zero behavior change for undeclared or not-yet-materialized fields).

Interaction with the existing self-heal (`runWithSchema` + `inner.ensureReady(true)` on "no such table"): after a parent cascade drops+recreates the table, the shadow column and trigger are gone from the recreated table. The vec-ensure cache must be reset alongside the schema self-heal so the shadow column/trigger/backfill are re-established on the reborn table. Practical approach: when `runWithSchema` catches a healable missing-table error and calls `inner.ensureReady(true)`, ALSO reset `vecEnsured = null` and re-run the vec-ensure before the retry (or fold vec-ensure into `runWithSchema`'s pre-op step and have the force-path reset both caches). ## 4. The four refinements as explicit build steps

1. NO write-side validation trigger. There is no CREATE TRIGGER on INSERT/UPDATE that validates dimensions. Dimension validation lives ONLY in the JS backfill (step 3.5.4): a wrong-dimension vector is skipped (shadow col left NULL), so at query time its row hits the JSON branch, `computeVectorDistance` returns null on the length mismatch, and the row drops out — exactly today's silent-drop semantics. No hard-fail-on-write. (Reason it must be JS-only: all node/edge types share ONE physical `firegraph` table so a validation trigger would fire on every write of every type; and a client-local dimension baked into a file-persisted trigger corrupts DBs shared by clients with different dimensions.)

2. KEEP the null-on-change trigger — pure SQL, AFTER UPDATE ONLY, `WHEN new.data IS NOT old.data`, body `UPDATE <t> SET <shadowcol> = NULL WHERE doc_id = new.doc_id`. Built by `buildVectorNullOnChangeTrigger`, created in the JS ensure step after the column exists. No INSERT trigger. When a row's `data` changes, its stale blob is nulled and the next findNearest backfill re-encodes it. The WHEN guard stops the backfill's shadow-only UPDATE from self-invalidating.

3. GUARD the ensure/backfill against READ-ONLY databases. The ALTER + backfill UPDATE would throw on a read-only handle BEFORE the CASE fallback runs. Detect read-only (or catch the write failure) and fall through: mark the field not-materialized, and have `compileFindNearest` emit the pure-JSON expression (never reference the missing shadow column). REQUIRED TEST: findNearest on a read-only handle returns correct results via the JSON branch with no throw.

4. ENCODE in JS during backfill, NOT via a SQL encode UDF. Keep the numeric distance UDF `firegraph_vector_distance_blob` (returns a NUMBER — verified on both drivers). The backfill selects `json_extract("data",'$.<field>')`, validates + `encodeVectorBlob` in JS, and binds the blob as a parameter to the UPDATE. Never introduce a BLOB-returning UDF.

## 6. Edge cases to keep in mind

- SELECT _ pollution: none. `rowToRecord` reads only named columns (a*type, a_uid, ..., data, v, created_at, updated_at), so the extra `\_\_vec*<field>`column returned by`SELECT _` is ignored — confirmed; do NOT rewrite the SELECT shape.
- Subgraph / per-table ensure: each subgraph is its own physical table; the wrapper re-wraps per subgraph, so vec-ensure runs (and caches) per resolved table. Thread `vectorDecls` through the `subgraph()` re-wrap.
- Firestore ignores `IndexSpec.vector` (and empty `fields`) — verified, no Firestore change.
- Nested vector field (`field: 'a.b'`): shadow column `__vec_a_b`, JSON path `$.a.b`. Validate every part; the naming must stay injective for the declared set (dedupe by field handles this).
- Driver blob param types: better-sqlite3 binds `Buffer`/`Uint8Array` as BLOB and hands the UDF a `Buffer`; node:sqlite binds `Uint8Array` (cast `as SQLInputValue`) and hands the UDF a `Uint8Array`. `computeVectorDistanceBlob` must accept both (Buffer is a Uint8Array subclass; honor `byteOffset`/`byteLength`). node:sqlite executor already spreads params as `SQLInputValue[]`; the backfill UPDATE uses the same executor path.
- Concurrency: the ALTER is guarded by `PRAGMA table_info`; a lost race (another connection added the column first) surfaces as "duplicate column name" on ALTER — catch it and treat the column as present. Recursive triggers are off, so the null-on-change UPDATE does not cascade.
- Do not regress the shared compiler: `compileSet`/`compileUpdate` in sqlite-sql.ts stay untouched and vector-free (D1/DO depend on them).
