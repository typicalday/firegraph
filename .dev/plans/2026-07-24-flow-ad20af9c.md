Lane: deep — new public API surface on a shared library plus changes to the SQLite FTS5 trigger/DDL/backfill layer across both drivers and the orphan sweep; wide blast radius and high reversal cost.

# Plan: opt-in per-type BM25 stats for SQLite full-text search

## Problem (what is actually broken)

Firegraph's SQLite backend answers `fullTextSearch({ aType, query, ... })` with one contentless FTS5 table per graph table, named `<t>_fts` (see `ftsTableName` in `src/internal/sqlite-search.ts`). Ranking uses `bm25(<t>_fts)`. BM25's IDF term — `log((N - n + 0.5) / (n + 0.5))` — is computed over the ENTIRE `<t>_fts` index (all `a_type` values together). The `aType` filter is applied only as a WHERE predicate on `<t>.a_type` AFTER scoring, in `compileFullTextSearch` (the JOIN/WHERE at ~lines 272-283). So documents of OTHER a_types still shift N and n, which changes the bm25 score and therefore the ORDER of the type-A results returned to the caller.

Consumer impact (from proposal): engram stores episodes plus derived facts/concepts in ONE subgraph and searches by `aType`. Consolidation inserts thousands of fact/concept rows that share vocabulary with episodes; this deflates episode IDF and measurably regresses episode search recall even though the query only asks for episodes.

## Goal

Let a caller get BM25 statistics scoped to a single `a_type`, so inserting rows of other a_types cannot move the rank/score of a within-type result — WITHOUT changing behavior for anyone who does not opt in, and WITHOUT breaking cross-type (no-aType or multi-type) search.

## Design decision (the open question, resolved — configured per-type FTS partition tables)

Candidates considered:

- (a) One FTS5 table per (graph table, a_type).
- (b) One FTS table + `a_type` aux column + per-type doc-frequency scoping at query time.
- (c) Something else.

Resolution — chosen: a CONFIGURED variant of (a). FTS5 exposes NO pure-SQL way to rescope `bm25()` to a subset of an index; its N and n are properties of the physical index. So (b) is impossible without hand-rolling an inverted index in SQL (per-type per-term document frequencies) — infeasible and slow. Naive (a) with DYNAMIC a*types is also rejected: our FTS sync is done by pure-SQL triggers that must run identically from ANY connection (the "any-connection invariant"), and you cannot parameterize a table name inside a trigger, so dynamic per-type tables would force table creation on the write path. Therefore I choose (a) realized as OPT-IN, CONFIGURED per-type partition tables: the caller declares which a_types get their own stats table up front; for each configured type `T` we build a supplementary FTS5 table `<t>\_fts*<mangleStorageScope(T)>`alongside the untouched shared`<t>\_fts`, kept in sync by literal-`WHEN`-guarded triggers (static SQL, any-connection-safe), sharing the existing `<t>\_fts_map` for VACUUM-stable rowids. A single-aType search MAY read the per-type table for per-type IDF; everything else reads the shared table exactly as today. This is the smallest mechanism that gives true per-type IDF while preserving the any-connection invariant and full backward compatibility.

## The five required constraints (carried into this plan)

1. BACKWARD COMPATIBLE. Default (no opt-in) builds exactly today's DDL: one shared `<t>_fts` with cross-type unified ranking, no extra tables, no changed ranking. Existing databases and callers work with zero migration. Per-type stats are strictly opt-in on BOTH the write side (backend option) and the read side (per-search flag).
2. CROSS-TYPE SEARCH UNCHANGED. A search with no `aType`, or that spans multiple a_types, must still run and rank against the shared `<t>_fts`. The per-type tables are supplementary; they never replace the shared index. If a per-search read opts in but no single maintained per-type table applies, fall back to the shared index (non-breaking).
3. FIREGRAPH CONVENTIONS. Factory functions, not classes. `.js` import extensions on relative imports. New errors extend `FiregraphError` with a string `code`. No default exports. New internal logic stays under `src/internal/`.
4. TESTS FOR BOTH DRIVERS (see Tests section) — better-sqlite3 (`tests/unit/sqlite-local-search.test.ts`) and node:sqlite (`tests/unit/sqlite-builtin-search.test.ts`, honoring `describe.skipIf(!HAS_NODE_SQLITE)`).
5. CORE-PATH CHANGE. This edits the FTS trigger/DDL core path, so the verify section below explicitly requires `/audit` to run before the builder marks the step done.

## Opt-in API surface (design the builder must implement)

Write side (which per-type tables are BUILT and MAINTAINED):

- Add `perTypeFtsStats?: string[]` to the SQLite backend options. Concretely add it to `SqliteBackendOptions` in `src/sqlite/backend.ts` and thread it through the two local factories: `LocalSqliteBackendOptions` in `src/sqlite/local.ts` and `NodeSqliteBackendOptions` in `src/sqlite/node-sqlite.ts`. The value is the list of `a_type` strings that get a dedicated stats table. Unset or `[]` = today's behavior exactly.
- This list must propagate to subgraph tables too. In `backend.ts`, `SqliteStorageBackend.subgraph(...)` and the `extraTableDDL` composition (currently `extraTableDDL: (table) => [...userExtraDDL, ...buildLocalSearchDDL(table)]` in both local factories) must pass the configured type list down so lazily created subgraph tables and self-heal recreations build the same per-type tables. Self-heal `healableTables` in `runWithSchema` (both drivers) must include the per-type FTS tables for the healed collection path.

Read side (whether a given search USES per-type stats):

- Add `perTypeStats?: boolean` to `FullTextSearchParams` in `src/types.ts` (default `false`/absent). When `true` AND the search targets exactly one `aType` AND that a*type has a maintained per-type table for the resolved graph table, `compileFullTextSearch` reads `<t>\_fts*<mangled>`and ranks with`bm25(<t>_fts_<mangled>)`. Otherwise it reads the shared `<t>\_fts` exactly as today.
- `compileFullTextSearch` needs to KNOW which per-type tables exist for the table it is compiling against. Pass the configured type list (or a resolved set) into the compile path the same way other backend config reaches it; do not query the DB schema at search time.

Do NOT export a per-type-specific type from the top-level `'firegraph'` entry beyond what already exists — `FullTextSearchParams` remains inference-only as documented. The new `perTypeStats` field rides on the existing params object. The write-side option is only on the SQLite subpath exports (`./sqlite-local`, `./sqlite-builtin`).

## Files to touch

- `src/internal/sqlite-search.ts` — THE core file.
  - New helper `perTypeFtsTableName(table, aType)` returning `` `${table}_fts_${mangleStorageScope(aType)}` `` (import `mangleStorageScope` from `../sqlite/catalog.js`; a_type strings can contain SQL-unsafe characters, so mangling is required — do not interpolate raw a_type into an identifier).
  - Extend `buildFtsDDL` / add a sibling builder to emit, for each configured a*type `T`: the `<t>\_fts*<T>`FTS5 virtual table (same column shape as`<t>\_fts`) and three triggers (ai/au/ad) whose bodies mirror `reindexBody`but target the per-type table AND carry a literal`WHEN new.a_type = '<T-escaped>'`(insert/update) /`WHEN old.a_type = '<T-escaped>'`(delete) guard. Reuse the shared`<t>\_fts_map` rowid (doc_id) — do NOT create per-type map tables. Escape the literal with standard SQL single-quote doubling.
  - Extend `buildFtsSyncStatements` / add a sibling to backfill each per-type table from base rows where `a_type = '<T>'` and purge ghosts, mirroring the existing shared-table sync.
  - `buildLocalSearchDDL(table)` gains the configured type list and appends the per-type DDL + sync after the shared DDL. Signature change: `buildLocalSearchDDL(table, perTypeFtsStats)`.
  - `compileFullTextSearch` — when `params.perTypeStats` is true and a single `aType` resolves to a maintained per-type table, JOIN/ORDER BY against `<t>_fts_<T>` instead of `<t>_fts`. The a_type WHERE predicate stays (defense in depth; the per-type table already only holds that type). All other branches unchanged.
  - `findOrphanedFtsTables(...)` — extend so cascade-dropped subgraph tables also drop their `<t>_fts_<T>` partitions. Currently it recognizes `<t>_fts` and `<t>_fts_map`; add the `<t>_fts_<suffix>` shape under the `<rootTable>_g_` prefix. Be careful the match does not treat `_fts_map` as a per-type partition named `map`.
- `src/sqlite/backend.ts` — add `perTypeFtsStats?: string[]` to `SqliteBackendOptions`; thread into `extraTableDDL` invocation, `subgraph(...)`, and `ensureReady`.
- `src/sqlite/local.ts` — add `perTypeFtsStats?` to `LocalSqliteBackendOptions`; pass into `buildLocalSearchDDL`; include per-type tables in `sweepOrphanedFtsArtifacts` and `runWithSchema` `healableTables`; forward the flag from search params to the compiler in `fullTextSearch`.
- `src/sqlite/node-sqlite.ts` — same changes as local.ts, mirrored for node:sqlite (`NodeSqliteBackendOptions`, its `wrapLocalSearchBackend` wiring, its self-heal path).
- `src/types.ts` — add `perTypeStats?: boolean` to `FullTextSearchParams` with a doc-comment explaining it is a no-op unless the backend was configured with matching `perTypeFtsStats` and the search targets a single aType.
- `src/client.ts` — `fullTextSearch` must pass `perTypeStats` through to `backend.fullTextSearch(params)` (it currently forwards params; confirm the new field is not stripped). No change to `checkQuerySafety` semantics.

## Edge cases the builder must handle

- a_type with SQL-unsafe characters (spaces, quotes, unicode, `/`, `-`): identifier via `mangleStorageScope`; literal in the trigger `WHEN` guard via single-quote doubling. Never raw-interpolate.
- Two configured a_types that mangle distinctly must not collide (mangling is injective — safe).
- Opt-in read flag set but backend did not configure that type → fall back to shared `<t>_fts`, no error.
- Opt-in read flag set with no `aType` or multiple a_types → shared `<t>_fts` (constraint 2).
- Subgraph tables created lazily AFTER first construction must still get per-type tables (thread the list through `subgraph`/`extraTableDDL`).
- Self-heal (dropped/corrupted FTS) must recreate per-type tables too.
- Backfill on a second connection / existing populated DB opting in later: `buildFtsSyncStatements` per-type backfill must populate from existing base rows, and be idempotent (purge ghosts + insert-missing), same pattern as the shared sync.
- Cascade subgraph drop: orphan sweep removes the per-type partitions.
- All emitted DDL/trigger statements MUST be idempotent (`CREATE ... IF NOT EXISTS`, `CREATE TRIGGER IF NOT EXISTS`) — `extraTableDDL` runs on every bootstrap and self-heal.
- VACUUM stability preserved by reusing the shared `_fts_map` doc_id indirection.

## Tests (both drivers — same cases in each file)

In `tests/unit/sqlite-local-search.test.ts` (better-sqlite3) and `tests/unit/sqlite-builtin-search.test.ts` (node:sqlite, under the existing `describe.skipIf(!HAS_NODE_SQLITE)` guard; pure-function describes keep no skip guard):

1. PER-TYPE ON isolates IDF: build a client with `perTypeFtsStats: ['<typeA>']`. Insert one type-A record; capture its rank/score in a single-aType search with `perTypeStats: true`. Insert MANY type-B records that share the query terms. Re-run the same type-A search with `perTypeStats: true` and assert the type-A record's rank AND bm25 score are UNCHANGED (the defect: today they change).
2. PER-TYPE OFF is byte-identical to today (default): the existing `'applies identifying filters'` cross-type test at `sqlite-local-search.test.ts:292-306` MUST still pass unchanged. Add an explicit assertion that with NO `perTypeFtsStats` configured and NO `perTypeStats` flag, results/order match the pre-change behavior (same as the shared-index path). Do not modify the existing test's expectations.
3. Control: with per-type OFF, the same "insert many type-B rows" sequence STILL shifts the type-A score (proves the mechanism, not the test, is what isolates — and proves default behavior is genuinely unchanged).
4. Fall-back cases: `perTypeStats: true` with an unconfigured aType, and `perTypeStats: true` with no aType / multiple a_types → uses shared index, returns sensible cross-type ranking, no error.
5. Lifecycle: backfill (opt-in on an already-populated DB), second-connection read, subgraph search with per-type stats, and cascade-drop orphan sweep of per-type partitions all still hold.
